## 적용한 결정 ID·버전 / 가정 / OPEN 항목

- 적용: R2-D02(필수 경로의 4개 상태 분리: `api_ready_at`·`precheck_ok_at`은 timestamp일 뿐, `NATIVE_ACCEPTED`는 ACCEPTED verification(receipt=1·block·proven position) 필요, `CONSUMED`는 evidence_consumptions 행 필요), R2-D05(OFFCHAIN_ASSERTION ⇔ trust=ASSERTED 강제; 자체 anchor는 PROVEN 불가), R2-D07(allocations는 cash_receipts만 참조; `excess`는 차주 refundable — `v_cash_ownership`에서 LP 적용액과 분리), R2-D12(PRODUCTION consumption→LOCAL_MOCK verification 금지: CHECK + 트리거; NATIVE_TESTNET도 profile 불일치 거부), GPU-076 §3(소비 키 = (env, sourceEventId) unique, locator unique, economicEventId unique; proof query key는 별도 테이블), GPU-012 AC-06(배분 합 = 수령액 CHECK, receipt 초과 금지), AC-08(`writeoffs.extinguishes_debt` 항상 false).
- 가정: economicEventId 형식 `{provider}/{account}/{TYPE}/{ref}`를 CHECK 정규식으로만 검사(의미 검증은 GPU-023/081). revision 충돌은 `out_of_order=true`로 명시 기록해야만 저장(S-03 fixture 의미). 회수 기록자는 operator/underwriter/guardian/treasury/system(keeper·차주·LP 불가).
- OPEN(다른 티켓): receivables의 revision↔economicEventId 규칙(GPU-031 OPEN → GPU-081), audit_log의 hash chain 계산은 앱 계층(GPU-025)에서 `prev_hash/entry_hash`를 채움(DB는 형식만 검사).
