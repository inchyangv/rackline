- 적용: R2-D01/D02(native 경로만 base 생성), R2-D03(서명/관리자/API 등록 경로 없음 — `test_ingest_roleGated_andNoDirectRegistration`), R2-D05(record ≠ 매출; 자체 검증 후 업무 전이만), **R2-D06**(checkpoint freshness gate: 누락/stale/revision gap/open 불일치 ⇒ 0; acceptedAt이 validity를 늘리지 않음 — proof validUntil은 claim에 고정), GPU-007 underwriting-policy §2 G-A/G-C/G-D(E2 유효·fresh 관측 필수), §3(advance/haircut), §5(caps), §6(checkpoint ≤ 7d, tolerance 0), GPU-012(cap = 모든 debt + 예약, cap=0 금지, 한도 하락 ≠ debt 삭제), GPU-076 §5–§6.
- **GPU-031 OPEN(revision↔economicEventId) 해소 방식**: ReceivableBook이 경제 ID를 consumer 입력이 아니라 proven 필드로 파생한다 — obligation 이벤트는 `(kind, obligationRef, revision)`, payout은 `(PAYOUT, ref, settlementSeq)`, checkpoint는 `(CHECKPOINT, 0, checkpointSeq)`. 같은 revision의 두 번째 proof·다른 log는 EvidenceBook `EconomicEventAlreadyRecorded`, 낮은 revision은 `RevisionStale`. **GPU-081 인수인계**: domain-model §2의 문자열 형식(`{providerId}/{account}/{eventType}/{ref}`)을 이 키와 1:1로 매핑하는 표(예: `…/OBLIGATION/inv-A#r2`)를 확정해야 함.
- 가정/제약(기록): (1) 파일럿은 source token ↔ loan asset 1:1(소수점 동일) — valuation ADR(GPU-008/040)은 별도. (2) `EvidenceMeaning`에 CHECKPOINT가 없어 SourceCheckpoint emitter는 registry에 CORRECTION으로 등록하고 book은 topic0로 판별·meaning 무시 → **OPEN(GPU-029/011 schema): `CHECKPOINT` meaning 추가**. (3) `ObligationRecognized`에 token 필드가 없어 채권 token은 첫 attributed payout에서 학습하고 facility source asset과 대조 → **OPEN(GPU-076/077/082): 내부 ABI에 token 추가 검토**. (4) 계정 revision 카운터 의미는 GPU-077 SourceEscrow와 동일(recognize/assign/correct/attributed payout/cancel 각 +1; unattributed payout 제외). (5) 노출 합산은 카테고리별 루프(파일럿 규모 가정; 대규모는 GPU-059 성능 한도).
- OPEN(다른 티켓): 위 (2)(3), GPU-036(manager가 reserve→vault fundDraw→consume 순서 소유), GPU-081(전 구간 연결·economic ID 표), GPU-082(공식 encoding fuzz).
